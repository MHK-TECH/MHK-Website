Building a RAG Pipeline That Actually Works

By M-Huzaifa Khilji � May 22, 2026 � 7 min read

RAG (Retrieval-Augmented Generation) sounds simple: retrieve relevant documents, feed them to an LLM, get an answer. In practice, every step has failure modes. Here's how to build one that works.

The Architecture

┌─────────┐     ┌──────────┐     ┌──────────┐     ┌─────────┐
│  Docs   │ ──▶ │ Chunking │ ──▶ │ Embedding│ ──▶ │ Vector  │
│         │     │          │     │          │     │   DB    │
└─────────┘     └──────────┘     └──────────┘     └────┬────┘
                                                        │
                              ┌──────────┐     ┌────────▼────┐
                              │   LLM    │ ◀── │  Retrieval  │
                              │  Answer  │     │   + Query   │
                              └──────────┘     └─────────────┘

Four stages. Each one can fail. Let's break them down.

Stage 1: Chunking

Your documents are too long for an embedding model. You need to split them into chunks. The strategy you choose determines everything downstream.

Chunking Strategies

StrategyHow It WorksBest ForDrawback
Fixed sizeEvery chunk is N tokensQuick prototypingSplits mid-sentence
Sentence-basedSplit on sentence boundariesGeneral textIgnores semantic boundaries
Paragraph-basedSplit on double newlinesWell-formatted docsVariable chunk sizes
SemanticSplit on topic changesResearch papers, reportsSlower, more complex
RecursiveHierarchical splittingMost use casesRequires tuning separators

The recursive character splitter is a good default:

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", ". ", " "]
)
chunks = splitter.split_documents(docs)

Rule of thumb: 500 tokens with 50 token overlap works for 80% of use cases. Start there, then tune.

Stage 2: Embedding

Each chunk gets converted to a vector (array of numbers). Similar chunks end up near each other in vector space.

Stage 3: Retrieval

The user asks a question. You convert it to a vector, find the most similar chunks, and return them. Simple concept. Tricky execution.

Retrieval Methods

  • Similarity search. Find chunks closest to the query vector. Fast, simple, often good enough.
  • MMR (Maximal Marginal Relevance). Balance similarity with diversity. Avoids returning 5 nearly identical chunks.
  • Hybrid search. Combine vector similarity with keyword matching (BM25). Best of both worlds.
  • Reranking. Retrieve broadly, then rerank with a cross-encoder. Expensive but dramatically improves quality.
# Hybrid search with reranking
from langchain.retrievers import EnsembleRetriever
from langchain.retrievers import ContextualCompressionRetriever
from langchain_cohere import CohereRerank

# Step 1: Retrieve broadly
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 20})
bm25_retriever = BM25Retriever(k=20)

# Step 2: Combine results
ensemble = EnsembleRetriever(
    retrievers=[vector_retriever, bm25_retriever],
    weights=[0.6, 0.4]
)

# Step 3: Rerank
reranker = CohereRerank(model="rerank-v3.5", top_n=5)
compression = ContextualCompressionRetriever(
    base_compressor=reranker,
    base_retriever=ensemble
)

Stage 4: Generation

You have the relevant chunks. Now you need the LLM to answer based on them.

The prompt template matters more than you think:

# Good RAG prompt
template = """Answer the question based ONLY on the context below.
If the context doesn't contain the answer, say "I don't have
enough information to answer this."

Context:
{context}

Question: {question}

Answer:"""

Key points:

  • Explicitly tell the model to use the context.
  • Tell it what to do when the answer isn't in the context.
  • Don't let it hallucinate. Force grounding.

Why Your RAG Gives Bad Answers

If your RAG system is giving bad answers, the problem is usually one of these:

  1. Bad chunking. The relevant information is split across chunks, so no single chunk has the answer.
  2. Bad retrieval. The embedding model doesn't understand the query semantics.
  3. Too few results. You're only retrieving 3 chunks. Try 10-20 with reranking.
  4. No reranking. The most relevant chunk isn't first. Reranking fixes this.
  5. Bad prompt. The LLM isn't being told to ground its answer in the context.
  6. Wrong model. Small models struggle with complex reasoning over retrieved context.

RAG is not plug-and-play. It's an engineering system with multiple interacting components. Get each stage right, measure retrieval quality separately from generation quality, and iterate.
